# Fusion Code Orchestrator v0.2.0 — Implementation Roadmap

> **For agentic workers:** Execute ONE task per session ("implement task N"). Use
> `superpowers:test-driven-development` inside each task. Read `CLAUDE.md` (created in Task 1)
> and only the task you were asked for. Do **not** commit or push — the owner commits manually.
> Steps are checkboxes (`- [ ]`); tick them as you go.

**Goal:** Turn Fusion from a promising prototype into a credible, evidence-backed open-source
tool that proves (or honestly disproves) whether a panel of small cheap LLMs can match a single
frontier model on coding tasks at lower cost and latency — usable from Claude Code, Cursor and Codex.

**Architecture (target):** One orchestration engine driven by declarative **strategies**
(`solo`, `panel`, `panel+refine`, `cascade`, …). The same engine runs in two modes:
**real mode** (MCP/CLI companion; minimal latency/cost, no judge overhead) and **benchmark mode**
(`fusion bench`; ground-truth scoring, blind judging, repeats, statistics, reports). Every LLM call —
including judge calls — goes through one cost ledger.

**Tech stack:** Python 3.12+, FastMCP, httpx (direct provider adapters), Pydantic v2, Typer/Rich,
SQLite, uv, pytest/ruff/mypy-strict.

## Part 1 — Analysis of v0.1.0 (what exists, what is wrong)

### 1.1 What v0.1.0 is
A Python MCP server (+ Typer CLI) exposing 9 tools. A request is redacted, classified/routed,
fanned out concurrently to a cheap panel (Haiku 4.5 + GPT mini + Gemini Flash), optionally refined
(mixture-of-agents round at `high` budget), scored by an LLM judge + heuristics, synthesized by a
stronger model (Sonnet), cost-compared against an Opus "baseline" (estimate, or real via opt-in
shadow A/B with a blind pairwise judge), and logged to SQLite with a lifetime-stats footer.
~15k lines, 103 passing offline tests, ruff + mypy-strict clean. Details live in README/ARCHITECTURE.

### 1.2 Idea-level findings (does the thesis hold?)
| # | Finding | Evidence |
|---|---------|----------|
| I1 | **The thesis is not demonstrated.** The only real benchmark (`evals/archive/2026-06-30-agent-harness-benchmark.md`, 2026-06-30) shows Fusion *more expensive and 5× slower* than Opus, and both arms failed the task. The harness itself (JSON-action agent loop that resets history each step) is not a credible measurement tool. | benchmark-results.md; `agent/loop.py` |
| I2 | **Pricing moved under the design.** Opus 5.5 ≈ $4/$20 per 1M, Sonnet 5.5 ≈ $2/$10 (secondary sources, Oct 2026 — verify in Task 5). A 3-model cheap panel + **Sonnet synthesizer** + 3 judge calls is roughly 1.1–1.4× the cost of one Opus 5.5 call for a typical 5k-in/1.5k-out task (illustrative). The synthesizer, not the panel, dominates cost. A cheap synthesizer (Luna/Haiku) or letting Claude Code aggregate would be ≈ 0.4–0.5× Opus. | arithmetic in Task 12 |
| I3 | **Quality is never measured against ground truth.** "Quality" = LLM-judge scores (Gemini Flash grading answers on 0–1 with 0.5 defaults) and a *keyword heuristic* (`final_eval.py`: confidence = 0.7 if the text contains "risk"/"confidence"). These cannot support a claim. | `evals/final_eval.py`, `evals/llm_judge.py` |
| I4 | **No ablations.** Mixture-of-agents literature shows heterogeneous mixes can underperform repeated sampling from the single best model. Nothing here tests panel size, refinement, synthesizer strength, or homogeneous-vs-heterogeneous panels. | no benchmark code for it |
| I5 | **Eval overhead sits on the critical path.** One judge call per panel answer (run *sequentially*, `orchestration/judge.py`), a "judge quality" call, then synthesis — adding cost and latency to every real request while the user only needs the answer. | `orchestration/judge.py`, `pipelines.py:494-517` |
| I6 | **Unused cost/latency levers:** no early exit when panel agrees (cascade), no hedging/early quorum, no prompt caching, no hard budget cap (`BudgetTracker` only warns), shadow baseline runs *after* the pipeline instead of concurrently. | `pipelines.py`, `budget.py`, `shadow.py` |
| I7 | **Agreement/disagreement is word-overlap on bullet lines** (`disagreement.py`) — too weak to drive routing or calibrated confidence. | `orchestration/disagreement.py` |

## Part 2 — Target state after v0.2.0
- **Evidence:** `fusion bench` runs ground-truth-scored studies across ≥ 100 tasks and ≥ 6 arms
  (frontier solo, cheap solo, cheap panel, +refine, +cascade, cheap-vs-strong synthesizer) with
  confidence intervals, a cost/quality Pareto chart and a per-task-type verdict
  ("Fusion cheaper? faster? better? yes / no / inconclusive"). Published in `docs/BENCHMARK_RESULTS.md`.
- **Full measurement picture per task and per arm:** seconds-to-complete (wall, p50/p90), money per task
  and **money per *solved* task**, input/output tokens, **output tokens/s** (effective and per-model decode
  rate), time-to-first-token, calls/retries — all from one ledger.
- **Completion judged by evidence, not vibes:** hidden tests, build/lint/type checks, **performance
  measurements**, **rendered screenshots** (vision-model judge for design/frontend), and a blind,
  tool-using "agentic judge" whose evidence is logged.
- **Real mode that is actually cheap/fast:** no judge on the critical path, parallelism everywhere
  it is safe, cascade/early-exit, cheap or Claude-Code-side aggregation, hard budget caps.
- **Models:** latest Anthropic/OpenAI/Google models, one verified catalog + dated pricing.
- **Integrations:** one-command install for Claude Code, Cursor and Codex; `uvx` (no clone); a
  Claude Code plugin with slash commands + advisor subagent; MCP progress notifications, resources, prompts.
- **UX:** compact answers, `fusion ask/doctor/models/bench`, live panel view, local dashboard.
- **Engineering:** staged pipeline, single cost ledger, layered user config, CI, ≥ 85% coverage on core,
  CHANGELOG, LICENSE, clean docs with no duplicated knowledge.

### PHASE B — Engine

### Task 6: Provider layer overhaul
*Suggested: Sonnet.* **Depends:** 5.

**Files:** `providers/{base,anthropic,openai,google,ollama,lmstudio,http_utils}.py`, new `providers/limits.py`, `tests/test_providers*.py`.

- [ ] **Shared clients:** each provider owns a lazily-created `httpx.AsyncClient` (HTTP/2, pooled), closed via `async def aclose()`;
  `create_pipelines`/MCP server lifecycle closes them.
- [ ] **Retries:** honour `Retry-After`, full-jitter backoff, retry only transient (429/5xx/timeouts), never retry 4xx; surface
  `error_type` (`RateLimit`, `Auth`, `Timeout`, `BadRequest`, `Server`).
- [ ] **Rate limiting:** `ProviderLimiter` (semaphore + optional RPM token bucket) per provider, configured in catalog/config.
- [ ] **Structured output:** `ModelRequest.response_schema: dict | None`; map to OpenAI `response_format: json_schema`, Anthropic
  tool-use/structured-output equivalent, Gemini `responseSchema`; fallback to current JSON-scrape when unsupported.
- [ ] **Anthropic prompt caching:** optional `cache_control` on the shared system+task prefix (`ModelRequest.cache_prefix=True`);
  record cache read/write tokens in `ModelResponse` and price them via `PriceSchedule`.
- [ ] **Token-accounting normalization (found in Task 5, required for correct costs):** `ModelResponse.input_tokens` must mean *total input including cached tokens*
  (the catalog cost model bills `input − cached` at the input rate and `cached` at the cached rate). Anthropic reports `input_tokens` *excluding* `cache_read_input_tokens`
  and `cache_creation_input_tokens` — add them back; Google reports thinking tokens in `thoughtsTokenCount` *outside* `candidatesTokenCount` and bills them as output — add
  them to `output_tokens`; OpenAI's `completion_tokens` already includes reasoning tokens. Add a per-provider contract test with fixture payloads for each rule.
- [ ] **Reasoning defaults (verified Oct 2026):** `gpt-6-luna` defaults to `reasoning_effort=medium` (values none/low/medium/high/xhigh/max) and in Chat Completions allows function
  calling only with `none`; `gpt-6.1-sol` has no `none`, and tool calling needs the Responses API; Claude Opus 5.5 / Sonnet 5.5 use adaptive thinking (effort parameter), Haiku 4.5
  has none; Gemini 3.8 Flash thinking levels are low/medium/high (`minimal` errors). Panel members should default to the cheapest effort that works, and `max_tokens` must leave room
  for thinking tokens (8192 may truncate answers). Decide per model in the catalog (`default_reasoning_effort`).
- [ ] **Params per model generation:** OpenAI `max_completion_tokens` + `reasoning_effort` where the catalog says supported;
  Anthropic sampling-param rule generalised via catalog flag (not a regex); optional extended-thinking budget field.
- [ ] **Security:** Gemini key goes in `x-goog-api-key` header, never the URL; redact keys from all error strings.
- [ ] Record `reasoning_tokens` / cached tokens consistently in `ModelResponse` for all providers.
- [ ] **Speed metrics at the source:** `ModelRequest.stream: bool` (SSE streaming for all three cloud providers; used in benchmark mode and
  optionally real mode). `ModelResponse` gains `ttft_ms` (time to first token), `decode_tokens_per_s` (= output_tokens / (latency − ttft)),
  `total_tokens_per_s` (= output_tokens / latency). Non-streaming calls leave `ttft_ms=None` and compute only `total_tokens_per_s`.
  Output-token counts come from provider usage, never from character counts.
- [ ] **Vision input:** `ModelRequest.images: list[ImagePart]` (PNG/JPEG bytes + media type) mapped to each provider's multimodal format; guarded by the catalog's
