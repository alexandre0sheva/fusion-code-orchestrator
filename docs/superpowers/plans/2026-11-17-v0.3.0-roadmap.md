# Fusion Code Orchestrator v0.3.0 — Implementation Roadmap

> **For agentic workers:** Execute ONE task per session ("implement task N"). Read `CLAUDE.md`, Part 3
> of this file and only the task you were asked for. Use `superpowers:test-driven-development` inside
> each task. Do **not** commit, push or tag: the owner does. When you start a task set its status in the
> tracker below to `in_progress`; when the quality gate passes set it to `done`, tick its checkboxes and
> add an **As built** paragraph under the task (what differs from the text, what was not verified).

**Goal:** turn "cheaper, slower, quality not shown" (the 0.2.0 verdict) into a panel that is **cheaper
and at least as fast as one frontier model, and better where answers can be checked**, and prove it
where it matters: inside a Claude Code session, end to end, with the host model's own tokens counted.

**Architecture (target):** the 0.2.0 engine (staged pipeline, strategies, one cost ledger, `fusion
bench`) gains (1) a price-tiered multi-vendor catalog of the latest models with OpenRouter as a fourth
provider, (2) a real mode that reads the workspace itself and spends less host context, (3) panel
diversity from *lenses* instead of temperature, (4) cheap *selection* instead of expensive *synthesis*,
(5) *verified generation*: the panel writes candidate patches **and** the checks that judge them, run in
a sandbox on a temporary copy (ideas ported from Google Research's Harness²: Propose–Probe–Compose,
blind ordered selection, script and guardrail synthesis, an evidence-backed experience library), and
(6) an end-to-end Claude Code A/B harness. A GitHub Pages site presents it.

**Tech stack:** Python 3.11+, FastMCP 4.x, httpx (direct adapters, no vendor SDKs), Pydantic v2,
Typer/Rich, SQLite, uv, pytest/ruff/mypy-strict; MkDocs Material for the site.

**Spec:** this file. Parts 1–2 (analysis and target state) are the design; there is no separate spec
document (the 0.1-era spec was deleted as stale). The 0.2.0 roadmap was retired when this file was
written; it is in git history (`git show 9f3faec:docs/superpowers/plans/2026-10-05-v0.2.0-roadmap.md`).

**Inputs this plan argues from:** `docs/BENCHMARK_RESULTS.md` (0.2.0 live study), the 0.2.0 roadmap,
Harness² (`github.com/google-research/harness2`, arXiv 2610.14224), provider pricing pages and
OpenRouter's public `GET /api/v1/models`, read on 2026-11-17.

### 1.5 What Harness² offers (and what ports)
Harness² optimises the *harness* around a fixed model (system prompt, guardrails, memory, tool guidance,
skills, subagents, scripts, plugins) with **Propose–Probe–Compose**: propose edits along two orthogonal
dimensions (INV = how the agent works, DOM = what a practitioner knows), probe them by running the task,
compose a final from *behavioural contrasts* without ground truth, then keep evidence-backed lessons in a
per-domain library for the next task.

| Harness² idea | Port to Fusion | Task |
|---|---|---|
| Orthogonal dimensions (INV/DOM) per candidate | Panel **lenses** for tasks whose answer is a list of findings (review, debug): each member covers a different area, and a `union` aggregator merges the findings and drops any finding not backed by the input | 7 |
| Blind selection with ordered criteria (delivery → conformance → fidelity checked against the source → consistency → fitness → finish; "length is not merit"; output is an id) | `select` aggregator for tasks whose answer is one whole solution (plan, architecture decision, `fusion_ask`, patch): every member answers the *whole* task in a different way, and a cheap judge returns an id + ≤ 6 lines instead of a synthesizer rewriting everything | 8 |
| Scripts, guardrails and plugins as the *cheap, enforceable* forms (prose can be skipped; a hook cannot) | **Script & guardrail synthesis**: the panel emits a repro/check script and invariants with every patch; candidates are cross-executed against all generated checks | 10, 11 |
| Validation before any rollout (trigger lines, named scripts exist, code compiles) | Static validation of generated scripts before they run | 10 |
| Subagent rule: worth it when the input is large and the answer small | Fusion reads big inputs itself and returns small answers (`fusion_digest`) | 5 |
| Harnessing-level recursion: library of `{cue, lesson, evidence, confidence}`, verdicts `helped / hurt / no effect / confounded` | Per-project **experience library** fed by run outcomes | 12 |
| Recursive improvement of the harness itself, parallel (wide) or sequential (deep) | `fusion tune`: Propose–Probe–Compose over Fusion's own prompt pack and strategies on the dev split | 13 |
| `KEEP_BASE` is a valid answer | "No issues found" is a valid, rewarded answer (fewer invented review findings) | 7, 8 |
| Evidence boundary and leak checks (graders' verdicts never reach the proposer) | Bench guard: hidden tests and rubrics never enter a prompt | 10, 14 |

Not ported: Harness²'s OpenCode/Codex executors, the professional benchmarks (JobBench, LAB,
WorkBuddy) and Vertex-only setup. Fusion stays an advisor behind MCP; Claude Code stays the executor.

## Part 2 — Target state after v0.3.0
- **Default real mode beats Opus 5.5 on cost (≤ 0.2x per solved task) and matches it on median latency**,
  using nano-tier models (Haiku 5.5, Luna, open-weight models via OpenRouter).
- **Difficulty routing (`strategy: auto`, the default):** easy requests answered by one nano model, harder ones escalated rung by rung only when the cheaper answer shows it is not enough.
- **A verified-generation path** (`fusion_propose_patch`) where cheap candidates are judged by
  panel-written checks run in a sandbox on a temporary copy, measured on executable tasks against Opus solo.
- **Evidence where it matters:** ≥ 120 tasks with ≥ 15 per category, neutral judges, and an end-to-end
  Claude Code A/B (executor × with/without Fusion) with total cost including host tokens.
- **Catalog:** only the latest models from Anthropic, OpenAI, Google and OpenRouter, tiers computed from price.
- **A public GitHub Pages site** with the docs, the benchmark report and the evidence.

## Part 3 — Global constraints (apply to EVERY task)
1. **Versioning:** all work is 0.3.0. One line per user-visible change under `## [Unreleased]` in
   `CHANGELOG.md`. `pyproject.toml` is bumped only in Task 19.
2. **No commits, pushes or tags.** Leave changes in the working tree; finish by listing changed files
   and updating the tracker row.
3. **Quality gate:** `uv run pytest -q && uv run ruff check src tests evals && uv run mypy` passes;
   `uv lock --check` passes after any dependency change.
4. **MCP boundary:** stdout is JSON-RPC in `fusion mcp`; log to stderr. Orchestration tools never
   write to the user's repository. Reading the workspace (Task 5) is read-only, confined to the project
   root, and refuses ignored and secret files.
5. **Never modify the user's projects (owner rule).** Anything that runs code — generated checks
   (Tasks 10–11), benchmark tasks (14), Claude Code A/B runs (15) — works in a **sandbox on a temporary
   copy** (`bench/sandbox.py`: no network, writes confined to the temp dir, time and output limits)
   and deletes the copy afterwards. Every such task has a test that hashes the source tree before and
   after a run and asserts it is byte-identical.
6. **Money: $15 of live API spend for the whole 0.3.0 roadmap (owner decision D1).** It counts 0.3.0
   spend only; earlier spending is ignored. Task 2 scopes the spend ledger by budget (`v0.3.0`, cap
   $15). Live calls only in the tasks the tracker gives a budget; each states its sub-budget before
   starting, checks `SpendLedger.check` before every call and records every call. Stop at $14.50 (keep
   $0.50 reserve).
   Everything else uses `MockProvider`, `SimulatedProvider` or `httpx.MockTransport`. Never print or
   commit keys.
7. **Prices and IDs:** values in this file are from 2026-11-17 and are inputs, not truth. Task 3
   re-verifies them from official pages and `GET /models`; every later task reads the catalog.
8. **Latest models only (owner rule).** Use the newest model of each family (Luna, Terra, Sol, Astra;
   Haiku, Sonnet, Opus, Fable; Gemini Flash and Gemini 4; the newest snapshot of each OpenRouter family).
   Older models stay only as `enabled: false` legacy entries. **Gemini 3.5 Flash-Lite and other
   Flash-Lite models are not used.**
9. **Tiers by price** (owner rule): a model's tier is computed from its blended price
   `blended = (3 × input + output) / 4` USD per 1M tokens (a 3:1 input:output mix, typical of review
   and debug calls). Thresholds: `nano` < $0.50 · `low` < $2.50 · `medium` < $6 · `high` < $12 ·
   `premium` ≥ $12. So $2/$10 → $4.00 → `medium`; $4/$20 → $8 → `high`; $0.10/$0.50 → $0.20 → `nano`.
   The weights and thresholds live in `catalog.yaml` (`tiering:`), never in code.
10. **OpenRouter privacy (owner decision D4):** requests go only to providers that **do not train** on
    prompts; providers that retain or log prompts without training on them are allowed. OpenRouter's
    per-request `data_collection: "deny"` is stricter than this (it drops every provider that stores
    data), so Fusion sends `data_collection: "allow"` and enforces "no training" as Task 4 describes.
    There is no switch that relaxes it silently.

## Review focus (inputs no task's happy path covers; each owning task adds the test)
1. Only `OPENROUTER_API_KEY` is set (no direct keys): every default strategy still runs, via OpenRouter routes of the same models (Task 4).
2. `paths` includes `.env`, a symlink out of the repo, a binary or a 50 MB file: refused or skipped with a reason, never sent to a model (Task 5).
3. A prompt crosses a long-context price threshold (Haiku 5.5 at 100K): the cost estimate and the `max_cost_usd` guard use the higher price (Task 3).
4. A catalog model returns 404 / is retired mid-run: the run falls back to the next model of the same tier and says so, instead of losing quorum (Task 6).
5. A generated check script loops forever, opens a socket or writes outside its temp dir: killed by the sandbox, scored as a failed check, never as a pass, and the user's repo is untouched (Tasks 10, 11).

- `Candidate(id, patch: str, checks: list[CheckScript], guardrails: list[str])`; `CheckScript(name, language: Literal["python","shell"], body: str, kind: Literal["repro","property","invariant"])`.

- `crosscheck(candidates, sandbox) -> Matrix[candidate_id, check_id] -> pass|fail|error|timeout` and `pick(matrix) -> candidate_id` (score = checks passed weighted by how many *other* candidates' checks agree; CodeT-style dual agreement; ties → `select` aggregator from Task 8).

- Strategy `aggregator: verified-synth` (generalises 0.2.0's `best-of-n-verified`: no longer needs the task's visible tests; uses them as extra checks when present).

- [ ] Evidence boundary: hidden tests, rubrics and reference solutions never enter a prompt; add a guard test like Harness²'s `assert_no_grader_verdicts`.
- [ ] The matrix and the reason for the pick are saved in the run record.

**Tests:** validation rejects network/escape/huge scripts; Review-focus item 5 (infinite loop → timeout → fail; socket → fail; write outside → blocked); the source tree is byte-identical after a run; a fixture where the majority patch is wrong but the cross-check picks the right one; non-discriminating checks discarded; leak guard.
